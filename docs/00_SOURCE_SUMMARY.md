# 00. 기획서 / 발표자료 기준 요약

이 문서는 업로드된 기획서와 발표자료의 내용을 **구현 기준으로 옮긴 요약**입니다. 이후 추가된 로그인/DB/배포 결정과 원자료의 요구를 구분합니다.

## 1. 원자료가 정의하는 문제

기존 모바일 보안 서비스는 탐지와 차단에 강하지만, 사용자가 경고를 이해하고 판단하고 실제 행동으로 옮기는 과정에는 공백이 있습니다.

닿음은 이 공백을 가족이 함께 메우는 서비스입니다.

핵심 문장:

```text
탐지 이후의 이해 -> 판단 -> 행동을 연결한다.
```

## 2. 사용자 역할

- 보호 대상: 스마트폰 보안 대응에 어려움을 겪는 부모/고령층
- 핵심 사용자: 부모의 스마트폰 보안을 걱정하는 성인 자녀
- 시스템: 탐지된 위험을 확인하고, 판단 가능한 근거와 쉬운 대응 문구로 바꿔 가족 대응을 돕는 역할

## 3. 원자료의 핵심 기능 3개

### 위험 정보 확인

- 의심 앱/보안 위협을 기존 탐지 데이터와 비교
- 위험 여부/유형 확인
- 위험도와 탐지 근거 제공

### 가족 공동 판단 지원

- 복잡한 보안 용어를 자녀가 이해할 수 있게 설명
- 부모의 보안 위험을 가족이 함께 판단할 수 있게 공유

### 쉬운 대응 행동 안내

- 부모에게 '무엇이 위험한가'보다 '지금 무엇을 해야 하는가'를 쉽게 전달
- 부모에게 보낼 안내문 생성/복사

## 4. AI/데이터 원칙

원자료에 포함된 역할:

- OCR: 앱 목록 스크린샷에서 앱 이름 추출
- 임베딩/RAG: 탐지 데이터와 유사도 비교
- LLM: 판정이 아닌 쉬운 설명/안내문 생성
- 분류 모델: 데이터 분석/신종 대응 가능성 실험, 서비스 최종 판정에 직접 사용하지 않음

## 5. 판정 원칙

```text
HIGH    탐지 DB와 강하게 일치
MEDIUM  유사도 임계값 이상
UNKNOWN 그 외
```

중요:

`UNKNOWN`은 `SAFE`가 아닙니다.

제공 데이터는 제한된 표본이므로 DB에 없다는 이유만으로 안전하다고 단정하지 않습니다.

## 6. 원자료의 제약/리스크

- 패키지명 결측
- OCR 오인식
- LLM hallucination
- 탐지 DB 미등록 앱
- 데이터가 제한된 기간의 표본
- 부모 스마트폰 정보를 자녀가 확인할 때의 프라이버시 우려

원자료가 제시한 대응 방향:

- 결측 데이터 사전 처리
- OCR 실패 시 직접 입력
- rule + RAG + model의 보조 구조
- LLM은 설명에만 사용
- 판단 불가를 명시
- 최소 수집

## 7. 원자료의 시스템 구조

```text
React
 -> Spring Boot
 -> FastAPI
 -> Pinecone / LLM
```

Spring Boot는 업로드/OCR 연동/결과 조립, FastAPI는 검색/판정/쉬운 설명/안내문 생성을 담당하는 방향입니다.

## 8. 발표자료의 모바일 방향

발표자료의 주요 UI가 스마트폰 세로 화면으로 제시되어 있으므로, 현재 구현은 React **모바일 웹 우선**으로 잡았습니다.

PPT에 '실시간 위험 알림' 방향이 보이지만, 기획서 MVP의 실제 사용자 시나리오는 부모가 스크린샷을 전달하고 자녀가 웹에서 분석하는 수동 흐름입니다. 따라서 자동 감시/실시간 이벤트는 확장 기능으로 분리합니다.
